# 设计理由和实测结论

技术上为什么这样做，以及每条背后测出来的数据。改动下面任何一条之前，先读它的原因。日期都是 2026 年。
怎么测、怎么判断的细节见 [design.md](design.md)。

## 一切都在浏览器里测

- **路由器从浏览器测**：页面在几个常见网关地址（`src/targets.mjs` 的 `GATEWAYS`）上找路由器，找到就多一行「路由器」，借此分开 Wi‑Fi 和宽带接入。
  - 这要靠 Chrome 的本地网络访问（Local Network Access）权限：用户允许后，`fetch(http://192.168.x.x, { targetAddressSpace: 'local' })` 不受混合内容拦截。
  - 其他浏览器没有这个权限，就没有这一行。不扫描整个网段。
- **代理是推断出来的**：页面不和代理软件通信，只靠浏览器自己的测量判断有没有代理、代理出了什么问题：
  - 时区和 Cloudflare 看到的出口国家对不上；
  - 国内网站直连和经代理的 Cloudflare 节点一对比，就分得出代理入口和代理出口；
  - 出口的网络和 Cloudflare 节点。

## UDP 用免费的公共 STUN，不用 Cloudflare TURN

**做法**：持续测 UDP 用公共 STUN 服务器（Cloudflare、Google，中国大陆另加小米、哔哩哔哩），从 STUN 的重传延迟推算丢包，不用 TURN 中继。

**为什么放弃 TURN**：最初的方案是只在用户点击时，用 Cloudflare Realtime TURN 做一次 20–60 秒的精确丢包测试。凭证短时有效，测完吊销，每天限量签发。实测发现这套限制管不住费用：

- Cloudflare TURN 每月前 1000 GB 免费，之后每 GB 0.05 美元。凭证一旦泄露，被拿去中继任意流量，就要付钱。
- 凭证的有效期最短只能设 60 秒，设 40 秒会被拒绝。
- 一个已吊销的 60 秒凭证（吊销接口返回 204），在第 73–81 秒仍然完整中继了 100/100 个包。
- 同一个凭证在 5、10、20、40、60 分钟后，仍然能分配到中继。

所以有效期和吊销都不起作用，只剩每日签发上限这一道闸，最坏情况下一个凭证至少能用一小时。原型（`testbed/` 的来源）里保留过这段代码，默认关闭。

**STUN 推算丢包的原理**：libwebrtc 发出的 STUN 请求没有回答时，会在 250、750、1750 ms 重发（`src/lib.mjs` 的 `RETX`）。回答比平时晚了一截，就说明前面丢了几次。IPv4 和 IPv6 各发一次请求，只看最快的回答会把另一边的丢包掩盖，所以每个回答都单独计数（`stunLoss`）。

**验证**（11-06，荷兰的一台 Linux VPS，Debian 11，无界面 Chrome）：用 iptables / ip6tables 在 INPUT 上随机丢弃回来的 STUN 响应，IPv4 和 IPv6 都丢，每档 5 分钟。数据在 `test/fixtures/stun-loss-2026-11-06.json`，测试里回放；测试台见 `testbed/`。

| 注入 | Cloudflare | Google |
| --- | --- | --- |
| 0% | 0% | 0% |
| 2% | 1.3% | 2.0% |
| 5% | 4.8% | 4.4% |
| 10% | 8.2% | 9.1% |

- **要丢回来的包（INPUT），不能丢发出去的包（OUTPUT）**。发出去的包在 OUTPUT 被丢时，`sendto()` 直接报错，Chrome 立刻重发，测试完全看不出丢包。
- **精度**：每个服务器每分钟大约 80 个回答，重传 1 次就是 1.25%。所以 5 秒一格只能看出「明显在丢」，准确的百分比要 5 分钟以上的数据。
- **开着代理软件的 TUN 模式时测不了**：代理的网络扩展先截走浏览器的 UDP，本机防火墙规则碰不到。注入 0% 和 10% 时，STUN 耗时分布完全一样。所以测试台要用不经过代理软件的机器。
- **浏览器自己关掉 WebRTC 的 UDP 时**（防泄露扩展、浏览器设置），所有探测都拿不到本地 UDP 地址。这时页面显示「测不了 UDP」，不判成「UDP 被拦」（`snapshot()` 的 `browserOff`）。

## 精确丢包用 WebRTC 回声服务器

STUN 推算要几分钟才准，所以另有一项按需的精确测试：点「精确测一下」时，页面向一台 WebRTC 回声服务器连续发 20 秒 UDP，分别算出去程和回程的丢包，再看 QUIC 能不能通。

- 回声服务器是固定月费的 VPS，按流量计费的中继（上面的 TURN）放弃了。
- 代码 `src/rtc.mjs` 是从 speed-test 复制的，两边要保持一致。
- 服务端代码在 [speed-test 的 `server/`](https://github.com/yt1988/speed-test/tree/main/server)，地址写在 `src/rtc.mjs` 里。服务端只接受白名单里的来源，所以自己部署本工具时，这一项要自己运行一份回声服务器。

## 调度放在专用 Worker 里

**实测**（11-06，Chrome 156，无界面浏览器的后台标签页，12 分钟）：

| 定时方式 | 后台标签页里实际多久触发一次 |
| --- | --- |
| 页面主线程的 setTimeout 链，没有 WebRTC 连接 | 每 60 秒 |
| 页面主线程的 setTimeout 链，开着 WebRTC 连接 | 每 2 秒 |
| 专用 Worker 里的定时器 | 每 1 秒，全程不变 |

所以调度和 HTTPS 探测都在专用 Worker（`src/worker-probe.js`）里跑。Worker 里没有 `RTCPeerConnection`，STUN 探测由 Worker 通知页面去做。页面睡着、采样不够时，那一格标成「未测」，不当成故障。

**专用 Worker 的 CSP 缓存**：专用 Worker 用的是它自己那个脚本响应头里的 CSP，脚本又按「永久不变」长缓存。所以 CSP 的哈希写进了 Worker 的文件名（`w.<hash>.js`），否则改了 CSP，访客一年内都拿不到新的。

## 其他实测和取舍

- **从中国大陆不开代理时**，最近的 Cloudflare 节点在境外（常见香港），不能当「近处」。这时国内网站当近处参照，Cloudflare 归到「远处」。开着代理时，国内网站单独成一行「国内直连」，「近处」变成「代理节点」，结论分成代理入口和代理出口。
- **前 20 秒的服务判断**只看超时：这时每个服务的「最好成绩」只有一两个样本，抖动会误报。远处和常用服务按最近 30 秒判断，因为它们 5 秒才测一次。每个目标的前两个样本是新连接在热身，不算。
- **满载延迟**下载 10 秒或 400 MB（先到为准），第一秒是爬坡不算。一条 674 Mbps 的线路 3.5 秒就下完了 300 MB，原来的上限太小，读不出东西。等级按 Waveform：A+ 少于 5 ms，A 少于 30，B 少于 60，C 少于 200，D 少于 400，再多是 F。
- **添加的服务测它的 favicon**：裸域名常常会跳转（bing.com → www.bing.com，2.1 秒对 0.25 秒），Worker 里的请求跟随跳转还会失败。所以添加时两种写法都试，留下更快的那个。
