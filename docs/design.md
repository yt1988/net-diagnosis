# 技术设计

网络诊断怎么测、怎么判断、怎么打分，和代码一一对应。为什么这样做、实测出来的依据，见 [decisions.md](decisions.md)。
数字和阈值以 `src/lib.mjs`、`src/targets.mjs`、`src/app.js` 为准，改了代码要同时改这里。

## 分层：路径上的每一段

页面同时测几条路径，每条代表从设备到服务之间的一段。某一段变差、它前面的段都正常，问题就在这一段。

| 段（页面上的一行） | 测什么 | 频率（前 20 秒加倍） | 代表 |
| --- | --- | --- | --- |
| 设备 | 专用 Worker 里 250 ms 定时器的迟到时间（p95） | 持续 | 设备或浏览器太忙时，其他数字都不可信 |
| 路由器 | 家里网关的 HTTP 往返（找到才有这一行） | 1 秒 | Wi‑Fi 和家里的网络 |
| 近处 | 最近的 Cloudflare 节点 `speed.cloudflare.com/__down?bytes=0` | 1 秒 | 宽带接入 |
| 远处 | AWS DynamoDB 在东京、法兰克福、弗吉尼亚的 `/ping` | 5 秒 | 跨境和长距离线路 |
| UDP | 向公共 STUN 服务器取公网地址 | 1 秒（轮流） | 游戏和通话用的 UDP |
| 常用服务 | 访客选的服务（默认 ChatGPT、Google、GitHub），测网站的 favicon | 5 秒 | 单个服务自己的问题 |

**中国大陆的特殊情况**（按时区和 Cloudflare 看到的出口国家判断）：

- **不开代理**：最近的 Cloudflare 节点在境外，归到「远处」；国内网站（百度、哔哩哔哩）当「近处」。
- **开着代理**（时区在中国、出口在别处）：国内网站单独成一行「国内直连」，代表自己的宽带；经代理到的 Cloudflare 节点这一行改叫「代理节点」，代表到代理服务器这一段；远处代表代理服务器之后的路。
- 两种情况下 STUN 都另加国内的服务器（小米、哔哩哔哩）。

**路由器**：开始测量时，同时试 10 个常见网关地址（`GATEWAYS`），优先选有网页回应的，其次选最快拒绝连接的。用的是 Chrome 的本地网络访问权限，`fetch(http://<网关>, { mode: 'no-cors', targetAddressSpace: 'local' })`，第一次会弹窗问访客。没找到就没有这一行。

## 探测

- **HTTPS**（`src/probes.mjs` 的 `https`）：`no-cors` 请求，读完响应体后等 20 ms，再从 Resource Timing 取时间。连接复用时，测到的就是一次往返。每个目标的前两个样本不算，那时连接还在热身。每个目标的第一个请求是新建连接，它比平时多出来的时间，就是「建连耗时」。
- **STUN**（`stun`）：建一个 `RTCPeerConnection`，只收集 server-reflexive 候选。每个回答单独记一个耗时，IPv4 和 IPv6 分开记；本地 UDP 地址和公网地址也记下来，用来发现地址变化，以及判断浏览器是不是关掉了 WebRTC 的 UDP。浏览器自己收集候选的开销（`stunOverhead`）开始时先测一次，再从每个耗时里减掉。
- **调度**：在专用 Worker 里（`src/worker-probe.js`）。HTTPS 探测在 Worker 里发；STUN 由 Worker 通知页面去做，因为 Worker 里没有 `RTCPeerConnection`。

## 判断：5 秒一格

每 5 秒（`WINDOW_MS`），对每个目标算一次窗口统计（`windowStats`：中位数、p90、最小值、超时次数）。远处和常用服务按最近 30 秒算，因为它们 5 秒才测一次。每个目标记住自己到目前为止最好的一格，作为它的「平时」。

**单个目标的状态**（`statusOf`，`f` 是平时最好的往返）：

| 原因 | 一般 | 变差 |
| --- | --- | --- |
| 超时 | 有超时 | 超时占 20% 以上 |
| 抖动（p90 − 最小值） | 超过 max(30, 0.5f) ms | 超过 max(60, f) ms |
| 比平时慢（中位数 − f） | 超过 max(25, 0.3f) ms | 超过 max(50, 0.6f) ms |
| 近处本身太远 | 中位数超过 80 ms | 超过 150 ms |
| 路由器本身太远 | 中位数超过 30 ms | 超过 80 ms |

一个请求都没回答，就是「不通」。常用服务只有抖动这一个原因时，最多判「一般」，因为服务的响应本来就有波动。

**UDP**（`stunLoss`、`udpStatusOf`）：用最近一分钟的回答。每次探测应得几个回答，取最常见的回答数。回答比基线晚过一档重传（250 / 750 / 1750 ms）就记一次丢包，少一个回答记 4 次（`RETX`）。丢包 2% 以上为一般，5% 以上为变差，全都没回答为不通。IPv4 和 IPv6 分开再算一次。连续 4 次以上探测都拿不到本地 UDP 地址，判为浏览器关掉了 WebRTC 的 UDP，显示「测不了」，不判成「被拦」。

**一组目标的状态**：一半以上变差或不通，这一组就是「变差」；有任何一般，就是「一般」。

## 归因：问题在哪一段

`attribute()` 按下面的顺序判断，命中一条就停，每条都附依据：

1. 浏览器报告断网 → **断网**；设备迟到 p95 超过 150 ms → **设备**。页面睡着的那几格不进归因，直接标「未测」（见下面「持续监控和事件」）。
2. 开着代理、有国内直连时：
   - 直连和近处或远处都变差 → **你这一侧**；
   - 直连正常、代理节点变差 → **代理入口**；
   - 直连和代理节点都正常、远处变差 → **代理节点之后**；
   - 只有直连变差 → **服务**（那几个国内网站）。
3. 没有代理时：
   - 近处和远处都变差 → **你这一侧**；
   - 近处正常、远处变差 → **跨境或远程线路**；
   - 只有近处变差、远处正常 → 只是最近的节点自己的问题，判为**服务**；
   - 只有近处、没有远处数据 → **你这一侧**（把握低）。
4. 部分常用服务变差 → **只有它们有问题**；全部变差 → **判断不了**。
5. UDP 变差或不通 → **UDP 丢包或被拦**；到同一个 Cloudflare 节点，UDP 往返超过 TCP 的 1.5 倍再加 30 ms → **UDP 比 TCP 慢很多**。
6. 都不是 → **没发现问题**。

最后两条细分：判成「你这一侧」时，如果测了路由器，路由器也变差就是 **Wi‑Fi 或家里的网络**，路由器正常就是**宽带接入**。没发现问题、但 IPv6 变差而 IPv4 正常时，判为 **IPv6 不稳定**。

**把握**（`confidence`）：每条规则先给一个基础把握（高、中、低）。同一个结论只持续了不到 2 格，降一档；持续 6 格以上，升一档。前 60 秒里，常用服务只有超时才算变差，因为这时它的「平时」只有一两个样本。

**顶部的结论**：从 20 秒起，每格用整次测量到现在的数据，再判断一次，作为页面顶部的结论。持续监控超过 2 分钟后，改用最近 60 秒的数据。

## 评分

| 项 | 怎么算 | 好 | 差 |
| --- | --- | --- | --- |
| 视频通话（MOS） | E-model 的简化式，见下 | 4 分以上 | 不到 3.6 分 |
| 网络游戏 | 每 10 分钟卡几次：往返比平时最好高出 100 ms 以上算一次，STUN 重传也算一次；再看丢包和抖动 | 2 次以内，丢包不到 1%，抖动不到 15 ms | 超过 6 次，或丢包 3% 以上、抖动 30 ms 以上 |
| 打开网页 | 建连耗时：各目标第一个请求减去它平时的往返，取中位数 | 不到 250 ms | 600 ms 以上 |
| 满载延迟 | 并行下载 10 秒或 400 MB（第一秒爬坡不算），期间近处往返的中位数比空闲时涨多少 | A+ 少于 5 ms，A 少于 30 | D 少于 400，再多是 F |

MOS：d 是单向延迟，J 是抖动，单位都是 ms；L 是丢包百分比。

```
d_eff = d + 2J + 10
R = 93.2 − d_eff / 40              （d_eff < 160）
R = 93.2 − (d_eff − 120) / 10      （其他）
R = R − 2.5L
MOS = 1 + 0.035R + 7×10⁻⁶ · R(R − 60)(100 − R)
```

页面上的往返除以 2 作为单向延迟。UDP 丢包有精确测试结果时用它，否则用 STUN 推算的丢包。

## 持续监控和事件

- **两种模式**：诊断测 2 分钟，20 秒先给出初步结论；持续监控一直测到按停止。
- **事件**（`Incidents`）：连续 2 格不正常（「判断不了」不算）就开一个事件，连续 3 格正常才关。满载测试期间的格子不算。
- **网络变化**：浏览器联网和断网、`navigator.connection` 的类型变化、STUN 看到的公网 IPv4 或 IPv6 地址变化，都记进事件记录，并在设备那一行的格子上标出来。
- **通知**：打开铃铛并允许通知后，每次开新事件发一条桌面通知。后台标签页的标题前会加一个「●」。
- **未测**：近处一格里不到 2 个样本，说明页面睡着了，这一格标成「未测」，不判断。

## 分享链接

结果写在链接路径里：`/<语言目录>/r/<编码>`，不经过服务器存储（`src/share.mjs`）。编码用 `~` 分隔字段，第一个字段是格式版本（现在是 1），依次是：测量时间、结论、把握、测了多久、模式、近处延迟、抖动、UDP 丢包、MOS、游戏等级、卡顿次数、建连耗时、满载等级和涨幅、国家、Cloudflare 节点、结论里点名的服务、事件数、各段的状态、近处那一行代表什么。

- 各段的状态每格一个字母，超过 24 格时按每段最差的状态压成 24 格。
- 国家和 Cloudflare 节点只有勾选后才写进去；IP 地址和运营商从不写进去。
- 读不了的编码，Worker 返回 404。Worker 读得了的，就把结论写进链接预览的标题，把数字写进描述（`src/worker.js`）。

| --- | --- |
| `src/lib.mjs` | 纯逻辑：统计、STUN 丢包、单个目标的状态、归因、评分、事件、把握、代理提示。有单元测试 |
| `src/targets.mjs` | 测哪些地址 |

| `src/share.mjs` | 分享链接的编码和解码 |

| `scripts/build.mjs`、`scripts/assets.mjs` | 生成 `public/`：各语言页面、站点地图、CSP；预览图 |

| `testbed/` | 在 Linux 机器上注入丢包、验证 STUN 推算的测试台 |

## 怎么验证判断

1. **单元测试**（`npm test`）：
   - 带标签的场景（Wi‑Fi、宽带接入、跨境、代理入口和出口、单个服务、UDP、IPv6 等）都要判对，没有故障时不能误报；
   - 回放测试台录下的 STUN 数据（`test/fixtures/stun-loss-2026-11-06.json`），推算的丢包要落在注入值附近。
2. **测试台**（`testbed/`）：改 STUN 推算方法后，在不经过代理软件的 Linux 机器上重新注入 0 / 2 / 5 / 10% 的丢包，看推算值。结果写进 decisions.md。
3. **真实网络**：改了归因规则，上线前在几种网络上各跑一次：离路由器很远的 Wi‑Fi、手机热点、开着代理。
